# Brief G1 — Implement OBD mode-01 PID 0x52 (ethanol fuel %) as a run-time-gated addition to `patches/ff_fuel`, on the smallest PID list (#39 optional half)

Brief F6 answered issue #39's optional second half — "optionally PID 0x52 in
the OBD handler" — with a **located, decided, not implemented** result
(`re/findings/obd.md`). The generic-OBD (SAE J1979 mode 01) stack **is** in
this image: the dispatcher, the dense class table, the five PID lists and the
four support bitmaps are all mapped and VERIFIED-STATIC. The bitmaps are built
in RAM from each record's `valid` byte, so a patch that owns a record can
advertise or hide PID 0x52 at run time by writing one RAM byte — no
calibration edit turns the bit on. But no free list slot exists, so the one
missing piece is a **longer list**, which F6 costed at **7 stock-instruction
words** on the smallest (B2) list and recommended for the follow-on brief.

This brief is that follow-on. It grows the B2 list by one entry so PID 0x52 is
answered, and makes the whole feature drive off a new `ff_pid52_enable` byte in
FFCAL001, default **0**, so the shipped image is byte-for-byte behaviour-identical
to today's until the human turns it on. It is the only wave-G brief allowed in
`patches/ff_fuel/**`. Wave G pair 1, parallel with G4. **Desk work only**:
nothing is flashed; every proof is in the emulator.

## Facts (VERIFIED-STATIC in `re/findings/obd.md` unless stated)
- **PID 0x52** = `A × 100 / 255` ethanol percent, one byte, class 2. The
  handler is `A = round(e_pct × 255 / 100)` clamped 0..255, in a two-byte
  record `{A, valid}`, `valid = ff_pid52_enable && ff_cal_ok()`.
- **The B2 list** (obd.md §3.2): three parallel arrays — `u32 record_ptr[3]`
  at 0x5C5DCC, `u8 pid[3]` at 0x5C5DD8, `u8 support_mask[3]` at 0x5C5DDB —
  packed with two bytes of 0x00 slack at 0x5C5DDE-0x5C5DDF. n = 3, checked at
  0x5D010 (`cmpwi r8,3`) and 0x5CD5C (`cmpwi r3,3`). Growing it to 4 needs the
  seven instruction edits F6 listed (obd.md §6, the table): three `addi`
  displacements in the reader at 0x5CCF4/0x5CD0C/0x5CD40, three in the builder
  at 0x5CFD4/0x5CFE4 and the two `cmpwi` bounds — plus the relocated 4-entry
  list (`u32×4 + u8×4 + u8×4` = 24 B) placed in free calibration inside r2 ±
  32 KB (r2 = 0x5C9FF0, window 0x5C2010-0x5D1FEF).
- **The support bitmap** is rebuilt every activation by `obd_pid_support_build`
  (0x5CBE8) from each record's `valid` byte (obd.md §4). PID 0x52 → byte index
  `(0x52-1)>>3 = 10` → RAM 0x80121F, mask 0x40. So with `valid = 0` the bit is
  clear and the extra loop iteration is side-effect-free; with `valid = 1` the
  bit appears and `01 52` answers. **No flash bitmap constant is edited.**
- **Free calibration for the relocated list.** The only erased (0xFF) runs in
  the r2 window are 0x5C2188 (56 B), 0x5C6AF6 (72 B) and 0x5C8262 (65 B), all
  **HYPOTHESIS-unused** (obd.md §8 item 3). Confirm the chosen run is genuinely
  free before using it: `tools/find_abs_refs.py --target <addr>` must show no
  reader, and it must sit inside a Bosch checksum block `patch_apply` can fix.
  Prefer a run that is not adjacent to live map cells. If none is safely free,
  fall back to placing the 24-byte list in the patch's own free flash and
  pointing the three reader/builder `addi` sites there instead — record which
  route you took and why.
- **These are edits to stock instructions**, not new hook words. They live
  inside the Bosch checksum block `desc 0x0A0070` (0x058000-0x05FFFF) and the
  calibration block holding the list. They are **not** trampolines and do not
  add to the patch's eight hook words; they are `build.data` inline edits in
  `patch.json`, generated by `patch_gen`, each with its `old` bytes asserted.
  The patch README's hook table stays at eight; a new "stock-instruction edits"
  subsection documents these seven plus the list relocation.
- **The run-time gate.** The enable byte cannot gate the *instruction* edits
  (they are always present), but it gates the record's `valid`, which gates both
  the answer and the bitmap bit. So with `ff_pid52_enable = 0` the grown list
  has a fourth entry whose `valid` is 0: `obd_pid_support_build` skips it, the
  bitmap is unchanged, and `01 52` returns "unsupported" exactly as stock —
  this is the bit-identity requirement, and it is behavioural, not byte-level
  (the seven instruction words and the 24-byte list differ from stock; the
  *observable OBD behaviour* is identical). State this distinction explicitly
  in the README and prove it in the emulator (task 3).
- FFCAL001 is at **v4, 332 B**. Bump to **v5**: append `ff_pid52_enable` (u8,
  default 0) past the current end, bump `VERSION`/`LENGTH` in `ffcal001.py`,
  mirror in `ff_state.h`, make `ff_cal_ok()` accept **v5 only**, regenerate
  `ffcal001_rows.csv`, and update `emu/models/flexfuel.py`, the tests and
  `logging/sessions/ff_fuel.json` in the **same commit**. The patch's `e_filt`
  (whole-percent, in `ff_state`) is the handler's input.
